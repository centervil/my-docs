## 📖 解説パート

### コンテナイメージの脆弱性管理とベストプラクティス

コンテナセキュリティの第一歩は、イメージ内の脆弱性を最小限に抑えることです。Amazon ECR（Elastic Container Registry）は、Amazon Inspectorと連携することで、プッシュ時や継続的なスキャンを行い、OSパッケージやアプリケーションの依存関係に含まれる脆弱性を特定します。

Dockerfileを作成する際は、「最小限の構成」を維持することが極めて重要です。具体的には、ルートユーザーでの実行を避け、`USER`命令を使用して非特権ユーザーでプロセスを起動します。また、ベースイメージには軽量なディストリビューション（Alpine LinuxやDistrolessなど）を選択し、不要なパッケージやツール（curl, git, シェルなど）を削除することで、攻撃者が利用できるツールを極限まで減らす「攻撃対象領域の最小化」を図ります。

### コンテナの権限管理：ECSタスクロールとEKS IRSA

コンテナがAWSリソースにアクセスする際、ノード（EC2インスタンス）に権限を付与するのではなく、コンテナごとに個別のIAMロールを割り当てるのが原則です。

ECSでは「タスクロール」を使用し、特定のタスク（コンテナ群）が必要とするAWSサービスへの権限のみを付与します。一方、EKSでは「IRSA (IAM Roles for Service Accounts)」を利用します。IRSAは、KubernetesのサービスアカウントとIAMロールをOIDC経由で紐付ける仕組みです。これにより、Pod単位で最小権限を適用でき、特定のPodが侵害された場合でも、その影響範囲を該当Podが必要とするリソースのみに限定できます。

```bash
# EKSにおけるIRSA設定の概念（ServiceAccountへのアノテーション）
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/my-app-role
```

#### 重要ポイント

* イメージスキャンを有効化し、CI/CDパイプライン内で脆弱性チェックを自動化する。
* コンテナは常に非特権ユーザーで実行し、ファイルシステムを読み取り専用（ReadOnlyRootFilesystem）に設定する。
* コンテナの実行権限には、ノードのIAMロールではなく、タスクロールやIRSAを優先的に使用する。

## 🏢 ケーススタディ

### ケース：特権コンテナを悪用したEKSクラスター侵害

ある企業で、開発者がデバッグ目的で「特権モード（privileged: true）」を有効にしたPodをクラスター内に配置しました。攻撃者はアプリケーションの脆弱性を突き、このコンテナへの侵入に成功。特権モードによりホストOSのデバイスへのアクセスが可能であったため、攻撃者はホスト上のkubelet認証情報を窃取し、クラスター全体を制御下に置くことに成功しました。

#### 問題点

* 特権コンテナ（privileged: true）が許可されており、ホストOSへのアクセスが可能になっていた。
* Pod Security StandardsやPolicyによる強制的な制限が導入されていなかった。
* コンテナの実行権限が過剰であり、侵害時の影響範囲がクラスター全体に及ぶ設計だった。

#### 対応策

* Pod Security Admissionを使用して、クラスター内で「Restricted」プロファイルを強制する。
* `securityContext`を適切に設定し、特権昇格（allowPrivilegeEscalation）を禁止する。
* Network Policyを導入し、Pod間の通信を最小限に制限する。

#### ケースから学ぶ教訓

* コンテナの特権設定は、ホストOSの侵害に直結する重大なリスクである。
* 「設定のガードレール」をポリシーとして自動適用し、手動設定による脆弱性を排除する。
