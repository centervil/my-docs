## 📖 解説パート

### Lambdaのセキュリティ設計

Lambda関数をセキュアに運用するためには、「実行ロール」「環境変数」「ネットワーク」の3点が重要です。

まず、**実行ロール**には「最小権限の原則」を適用します。関数が必要とするリソース（S3バケットやDynamoDBテーブルなど）のみにアクセス許可を与え、ワイルドカード（*）の使用は避けます。次に、**環境変数**の保護です。DBの接続文字列やAPIキーなどの機密情報を環境変数に含める場合、プレーンテキストでの保存は避け、AWS KMSで暗号化します。これにより、万が一設定が漏洩しても情報が保護されます。

最後に、**VPC内Lambdaのネットワーク設計**です。Lambdaをプライベートサブネットに配置することで、インターネットからの直接アクセスを遮断し、セキュリティグループで通信を厳密に制御します。ただし、VPC内に配置するとインターネットへのアクセスが失われるため、NAT GatewayやVPCエンドポイントの適切な設定が不可欠です。

### API Gatewayの保護と認証

API Gatewayは公開エンドポイントとして機能するため、多層的な防御が必要です。

第一に、**AWS WAFとの連携**です。SQLインジェクションやクロスサイトスクリプティング（XSS）、悪意のあるボットからの攻撃をフィルタリングするために、API GatewayにWAFを関連付けます。

第二に、**認可メカニズム**です。Lambda Authorizerを使用することで、API実行時にカスタムロジックによる認証（トークンの検証など）を組み込むことができます。また、リソースポリシーを活用することで、特定のIPアドレスや特定のIAMロールからのみAPIへのアクセスを許可するといった制御が可能です。

```bash
# Lambda関数の環境変数をKMSで暗号化する例（AWS CLI）
aws lambda update-function-configuration \
    --function-name MyFunction \
    --environment "Variables={DB_PASSWORD=secret_value}" \
    --kms-key-arn arn:aws:kms:region:account-id:key/key-id
```

#### 重要ポイント

* Lambda実行ロールは、関数が実行するアクションとリソースにのみ限定する。
* 機密情報はKMSで暗号化し、環境変数の保護を徹底する。
* API GatewayにはWAFを適用し、Lambda Authorizerで認証を強化する。

## 🏢 ケースステディ

### ケース：Lambdaコードへのアクセスキーのハードコード

ある開発者が、S3バケットへアクセスするためのIAMユーザーのアクセスキーをLambda関数内にハードコードしてコミットし、そのコードが外部リポジトリへ流出した。

#### 問題点

* アクセスキーの権限が広範囲に及んでいる可能性があり、不正利用のリスクが高い。
* コードの静的解析やシークレットスキャンが導入されておらず、検出が遅れた。
* 認証情報のローテーションが考慮されておらず、即座に無効化しても業務への影響が出る。

#### 対応策

* 即座に該当のIAMアクセスキーを無効化・削除する。
* CloudTrailで当該キーによる不正なAPIコールがないか調査し、影響範囲を特定する。
* IAMロール（実行ロール）への切り替えを行い、ハードコードを排除する。
* Secrets Managerを活用し、認証情報の自動ローテーションを導入する。

#### ケースから学ぶ教訓

* ソースコードへの認証情報の埋め込みは厳禁である。
* 認証情報は常に一時的なもの（IAMロール等）を使用する。
* CI/CDパイプラインにシークレット検出ツールを組み込み、自動的にブロックする。

## 📋 今日のまとめ

* Lambdaのセキュリティは、実行ロールの最小権限とKMSによる環境変数の保護が基本である。
* VPC内のLambda運用には、NAT Gateway等のネットワーク設定とセキュリティグループの制御が不可欠である。
* API GatewayはWAFとLambda Authorizerを組み合わせ、多層的な防御を構築する。
