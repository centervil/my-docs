## 📖 解説パート

### AWSにおけるインシデントレスポンス（IR）フレームワーク

AWS環境でのインシデント対応は、NISTやSANSが定義する標準的なプロセスに基づき、以下の6つのフェーズで構成されます。

1. **準備（Preparation）**: ツール（GuardDuty, CloudTrail等）の有効化や、アクセス権限の付与、自動化スクリプトの事前準備。
2. **検出（Detection）**: GuardDutyやSecurity Hubを通じた異常の特定とアラートの通知。
3. **封じ込め（Containment）**: インシデントの拡大を防ぐための隔離（Security Groupの更新やIAMロールの剥奪）。
4. **根絶（Eradication）**: 原因の特定と排除（悪意あるプロセスの停止や侵害されたリソースの削除）。
5. **復旧（Recovery）**: システムの正常化とバックアップからのリストア。
6. **教訓（Lessons Learned）**: インシデントの振り返りと、再発防止策の策定。

特にAWSでは、マネージドサービスを活用した自動化が鍵となります。手動対応を減らすことで、MTTR（平均復旧時間）を大幅に短縮可能です。

### EC2インスタンスの隔離とフォレンジック手順

EC2インスタンスへの侵害が疑われる場合、証拠を維持しつつ被害を最小限に抑える「隔離」が最優先です。

1. **隔離**: 対象インスタンスのSecurity Groupを「通信を一切拒否する（インバウンド・アウトバウンド共に0.0.0.0/0を削除）」設定に変更します。インスタンスを停止せず、ネットワークから切り離すのがポイントです。
2. **スナップショット取得**: EBSボリュームのスナップショットを作成します。これにより、OS内部のログや攻撃者が配置したマルウェアの痕跡を保存します。
3. **フォレンジック転送**: 作成したスナップショットを、隔離された別の「フォレンジック専用AWSアカウント」に共有し、そこでボリュームをマウントして詳細な調査を行います。

```bash
# Security Group変更の例（AWS CLI）
aws ec2 modify-instance-attribute --instance-id i-xxxx --groups sg-deadbeef
```

#### 重要ポイント

* **証拠の保全**: 侵害されたインスタンスをいきなり終了（Terminate）させると揮発性のデータが消えるため、必ずスナップショットを取得してから調査する。
* **権限の最小化**: インシデント対応を行うオペレーターには、調査に必要な権限のみを付与し、特権の乱用を防ぐ。
* **自動化の活用**: EventBridgeとLambdaを組み合わせ、検知から隔離までのフローを自動化することで、人的ミスを減らす。

## 🏢 ケーススタディ

### ケース：GuardDutyによるC&C通信の検知

GuardDutyがEC2インスタンスに対して`Backdoor:EC2/C&CActivity.B`（攻撃者の制御サーバーとの通信）を検知しました。このインスタンスはWebサーバーとして公開されており、顧客データにアクセス可能なロールが付与されています。

#### 問題点

* インスタンスが攻撃者のサーバーと通信しており、機密データが流出する恐れがある。
* 侵害されたインスタンスが踏み台となり、社内ネットワークへ攻撃が拡散するリスクがある。
* インスタンスを強制終了すると、攻撃者が残した痕跡（ログやツール）が失われ、原因究明が困難になる。

#### 対応策

* 即座に該当インスタンスを隔離用Security Groupに切り替え、外部通信を遮断する。
* インスタンスに付与されているIAMロールを一時的に無効化し、データアクセス権を剥奪する。
* EBSスナップショットを取得し、フォレンジック調査を開始する。
* システムログ（CloudTrail, VPC Flow Logs）を確認し、侵害の起点を調査する。

#### ケースから学ぶ教訓

* ネットワーク分離は「停止」ではなく「セキュリティグループによる封じ込め」を優先する。
* インシデント発生時に備え、調査用アカウントへのクロスアカウント権限を事前に構成しておく必要がある。
* 権限管理を適切に行い、Webサーバーが必要以上のデータアクセス権を持たないように設計する。
