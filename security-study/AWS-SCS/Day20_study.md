## 📖 解説パート

### ACMによる証明書のライフサイクル管理

AWS Certificate Manager (ACM) は、SSL/TLS証明書のプロビジョニング、管理、およびデプロイを簡素化するマネージドサービスです。パブリック証明書の場合、ACMはDNS検証またはEメール検証を通じて所有権を確認し、証明書を発行します。特筆すべきは「更新の自動化」であり、ACMと統合されたAWSサービス（ALB, CloudFront, API Gatewayなど）では、有効期限が近づくと自動的に証明書が更新されます。これにより、手動管理に伴う証明書の期限切れによるサービス停止リスクを排除できます。

プライベート証明書についても同様に管理が可能ですが、こちらは社内ネットワークや閉域網での利用が主となります。ACMを利用することで、従来のオンプレミス環境で必要とされていた複雑なPKI管理コストを大幅に削減し、コンプライアンス要件に準拠した証明書発行プロセスを構築できます。

### ACM Private CAと失効管理

ACM Private CAは、独自のプライベート認証局（CA）を構築できるサービスです。企業内のマイクロサービス間通信やVPN、IoTデバイスの認証など、閉域網内の信頼関係を構築する際に不可欠です。

プライベートCAを運用する上で最も重要なのが「失効管理」です。証明書が侵害された場合、即座にその無効性を周知する必要があります。ACM Private CAでは以下の手法でこれを実現します。

* **CRL (Certificate Revocation List):** 失効した証明書リストをS3に公開し、クライアントが定期的に参照する仕組み。
* **OCSP (Online Certificate Status Protocol):** クライアントがリアルタイムで証明書の有効性を問い合わせる仕組み。

これらを適切に設計することで、万が一の漏洩時にも被害範囲を限定することが可能です。

```bash
# ACM Private CAの作成例（CLI）
aws acm-pca create-certificate-authority \
    --certificate-authority-configuration KeyAlgorithm=RSA_2048,SigningAlgorithm=SHA256WITHRSA,Subject="{CommonName=MyPrivateCA}" \
    --certificate-authority-type SUBORDINATE
```

#### 重要ポイント

* ACMによるパブリック証明書の自動更新は、AWSサービスとの統合が前提。
* プライベートCAは、閉域網内の通信における「信頼の起点」となる。
* 失効管理（CRL/OCSP）の設計は、セキュリティインシデント発生時の対応速度に直結する。

## 🏢 ケーススタディ

### ケース：マイクロサービス間通信のmTLS導入

社内のマイクロサービスアーキテクチャにおいて、サービス間の通信を暗号化し、かつ相互にクライアント証明書を検証する「mTLS（相互TLS）」の導入が求められています。各サービスはコンテナで稼働しており、証明書を安全に配布・管理する必要があります。

#### 問題点

* サービス数が増加するにつれ、手動での証明書配布・更新が困難。
* 認証情報の漏洩が発生した場合の迅速な失効手段が確立されていない。
* 通信パスごとに異なる信頼関係を管理する仕組みが不足している。

#### 対応策

* ACM Private CAをルートCAとして配置し、各マイクロサービスに証明書を発行する。
* コンテナ起動時にAWS Private CA連携ツールを利用し、短命な証明書を自動取得する。
* 失効管理としてS3にCRLを公開し、各サービスが定期的に検証を行う構成にする。
* サービスメッシュ（AWS App Mesh等）と統合し、証明書検証をサイドカーにオフロードする。

#### ケースから学ぶ教訓

* ゼロトラスト環境では「ネットワーク境界」ではなく「証明書」が信頼の根拠となる。
* 証明書の有効期間を短く設定することで、漏洩時のリスクを最小化できる。
* 自動化されていないPKI運用は、必ずボトルネックと脆弱性を生む。
