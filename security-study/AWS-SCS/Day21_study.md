## 📖 解説パート

### User PoolsとIdentity Poolsの役割と連携

Amazon Cognitoは、大きく分けて「User Pools」と「Identity Pools」という2つのコンポーネントで構成されています。

**User Pools**は、ユーザーディレクトリの役割を果たします。ユーザーのサインアップやサインイン、プロフィール管理、MFA（多要素認証）の強制、パスワードポリシーの設定など、「誰がログインしているか」というアイデンティティを管理する場所です。

一方、**Identity Pools**は、AWSリソースへのアクセス権を制御する「認可」の役割を担います。認証が成功したユーザーに対して、一時的なAWS認証情報（IAMロール）を払い出すことで、S3バケットへのファイルアップロードやDynamoDBへの書き込みといったAWSサービスへの直接アクセスを可能にします。

一般的な連携パターンとして、ユーザーはまずUser Poolsで認証を行い、JWT（JSON Web Token）を取得します。次に、そのトークンをIdentity Poolsに提示することで、適切なIAMロールに紐づいた一時的なAWS認証情報を取得するというフローをとります。

### セキュリティ機能と最小権限の設計

Cognitoでは、認証フローを強化するために「Advanced Security Features」を活用できます。これには「アダプティブ認証」が含まれ、ユーザーのログイン場所やデバイス情報などからリスクを評価し、不審なアクセスに対してはMFAの要求やパスワードリセットを自動的に実行します。

また、外部ウェブアプリケーションからAWSリソースを利用させる際は、IAMロールの設計が非常に重要です。Cognito Identity Poolsを利用する場合、認証されたユーザー用と未認証（ゲスト）ユーザー用にそれぞれIAMロールを割り当てることが可能です。

ここで重要なのは、**「最小権限の原則」**を適用することです。特定のS3プレフィックスへのアクセスのみを許可するIAMポリシーを作成し、Cognito経由で取得した一時的な認証情報に適用することで、万が一認証情報が漏洩した場合の被害を最小限に抑えます。

#### 重要ポイント

* User Poolsは「認証（誰か）」、Identity Poolsは「認可（何ができるか）」を担う。
* Advanced Security Featuresにより、リスクベースの認証やMFA強化が自動化できる。
* Identity Poolsで生成するIAMロールには、必要なサービス・リソースのみに絞ったIAMポリシーを適用する。

## 🏢 ケーススタディ

### ケース：モバイルアプリからのセキュアなS3アクセス

ある企業が、ユーザーごとに異なるフォルダへ写真データをアップロードするモバイルアプリを開発しました。すべてのユーザーが同じS3バケットを利用しますが、他人のデータにはアクセスできないようにする必要があります。

#### 問題点

* ユーザー間でデータの閲覧・削除ができてしまうリスクがある。
* アプリ内に固定のAWS認証情報を埋め込むと、漏洩時に被害が拡大する。
* 認証と認可の境界が曖昧で、権限管理が複雑化している。

#### 対応策

* Cognito User Poolsでユーザーを管理し、Identity Pools経由で一時的な認証情報を払い出す。
* IAMポリシーで `s3:prefix` 変数を使用し、ユーザーIDに基づいたフォルダアクセスのみを許可する。
* アダプティブ認証を有効にし、異常なログイン試行を検知・ブロックする。
* MFAを必須とし、パスワードの使い回しによる不正アクセスを防止する。

#### ケースから学ぶ教訓

* クライアントサイドに長期的なAWS認証情報を持たせてはならない。
* 認可にはCognito Identity Poolsを活用し、動的な権限制御を行う。
* IAMポリシーの変数を利用して、ユーザー単位でアクセス範囲を動的に制限する。
