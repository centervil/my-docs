## 📖 解説パート

### 複合的な設計問題へのアプローチ

試験におけるアーキテクチャ問題では、単一のサービスだけで解決するケースは少なく、複数のサービスを適切に組み合わせる必要があります。例えば「マルチアカウント環境でのログ集約と監視」を問われた場合、CloudTrail、CloudWatch、Amazon S3、そして組織全体を管理するAWS OrganizationsやAWS Control Towerの連携が不可欠です。

解答を導く際は、まず「要件の優先順位」を整理してください。問題文に「運用負荷を最小化せよ」とあればマネージドサービス（GuardDutyやSecurity Hub等）が優先され、「コスト効率」が重視されれば、データの保存期間やライフサイクルポリシーの設計が鍵となります。常に問題文のキーワードから「どのドメインのどのサービスが適しているか」を即座に引き出せる状態を目指しましょう。

### 選択肢を見極めるための判断ロジック

試験で最も迷いやすいのが「似たような機能を持つサービス」の選定です。これを見極めるには、以下のロジックを意識してください。

* **コスト効率:** データのライフサイクル設定や、転送量の最適化、あるいはサーバーレス構成か、インスタンスベースか。
* **運用負荷:** 独自構築が必要なもの（EC2上のソフトウェア）か、フルマネージドサービス（AWS WAFやManaged Rules）か。
* **セキュリティ強度:** 最小権限の原則に合致しているか、暗号化の適用範囲は適切か、監査証跡は改ざん不能か。

#### 重要ポイント

* 問題文の制約条件（「最小限の変更で」「既存環境を維持しつつ」など）を絶対に見落とさない。
* サービス選定に迷った際は、AWS公式が推奨するベストプラクティス（Well-Architected Framework）に基づいている方を選ぶ。
* 過去問演習後は「なぜその選択肢が正解で、他が不正解なのか」を、ドキュメントの該当箇所を参照して言語化する。

## 🏢 ケーススタディ

### ケース：金融系企業のマルチアカウント・セキュリティ基盤構築

ある金融企業が、AWS Organizationsを利用したマルチアカウント環境へ移行します。全アカウントのログを一元管理し、異常検知を自動化しつつ、セキュリティチームによる中央集権的な監査を実現したいと考えています。しかし、各開発チームには一定の自由度を与えたいという要件があります。

#### 問題点

* 各アカウントでログが分散し、可視性が欠如している。
* セキュリティ担当者が手動で全アカウントを確認するのは非効率。
* 開発チームの権限が広すぎると、設定変更によるリスクが生じる。

#### 対応策

* AWS CloudTrailとAmazon S3を利用し、ログアーカイブ用のアカウントへ証跡を集約する。
* AWS Security Hubを有効化し、Organizationsと連携して全アカウントのセキュリティスコアを一元管理する。
* SCP（サービスコントロールポリシー）を活用し、ガードレールとして重要なセキュリティ設定の変更を制限する。
* IAM Identity Centerによる一元的なID管理と、Permission Boundariesによる権限の最大範囲の制限を行う。

#### ケースから学ぶ教訓

* セキュリティは「一元管理（集中）」と「権限委譲（分散）」のバランスを設計することが重要。
* ガードレール（SCP等）を先に設定することで、開発者の自律性と安全性を両立できる。

## 📋 今日のまとめ

* 複合的な設計問題では、問題文の制約（コスト・運用・強度）を最優先に考慮する。
* サービス選定は「マネージドサービスによる自動化」を優先的に検討する。
* 模擬試験での誤答は、単なる知識不足ではなく「設計思想のズレ」として分析し、ドキュメントで再確認する。
