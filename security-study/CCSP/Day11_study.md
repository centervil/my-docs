## 📖 解説パート

### クラウドにおける冗長化とDR設計の基本

クラウドにおけるDRの最大のメリットは、物理的な資産を所有することなく、論理的な設定のみで強固な冗長性を確保できる点にあります。クラウドのDR設計では、単一のデータセンター（DC）の障害を超え、リージョン（地域）をまたいだ構成が不可欠です。

まずはクラウド特有のアーキテクチャを理解しましょう。
* **Availability Zone (AZ) 設計:** 単一リージョン内の独立した電源・冷却・ネットワークを持つデータセンター群です。AZ間の冗長化により、DC単位の障害に対応します。
* **マルチリージョン冗長化:** 地震や大規模な地域停電など、リージョン全体が機能停止するリスクに備えるための構成です。
* **Cross-Region Replication:** データを物理的に離れた別のリージョンへ自動複製する機能です。これにより、片方のリージョンが壊滅的な被害を受けた場合でも、データを別のリージョンで復旧させることが可能となります。

### クラウドDRの構成パターンとRTO/RPO

クラウドDRでは、コストと復旧速度のバランスに応じて、主に以下の3つのパターンが採用されます。

1. **Pilot Light（パイロットライト）:**
   最小限のコアサービスのみをDRサイトで常時稼働させ、障害発生時に必要なリソースを一気にスケールアップさせる手法です。コストは低いですが、復旧には一定の時間がかかります。
2. **Warm Standby（ウォームスタンバイ）:**
   本番環境の縮小版を常に稼働させておく手法です。Pilot Lightよりも迅速に復旧でき、RTO（目標復旧時間）を短縮可能です。
3. **Multi-Site Active-Active（マルチサイト アクティブ・アクティブ）:**
   全てのリージョンでトラフィックを負荷分散して処理します。RTO/RPOはほぼゼロですが、コストは最も高くなります。

また、データレプリケーションには「同期」と「非同期」の選択が伴います。同期レプリケーションはデータ損失（RPO）を最小化しますが、ネットワーク遅延がアプリケーションパフォーマンスに影響を与えます。一方、非同期はレイテンシーを抑えられますが、わずかなデータ損失が発生するリスクがあります。

#### 重要ポイント

* **RTO/RPOの明確化:** ビジネス要件に応じ、許容できる停止時間(RTO)とデータ損失量(RPO)を定義する。
* **共有責任モデルの再確認:** CSPはインフラの復旧を保証しますが、アプリケーションやデータの復旧計画は利用者の責任である。
* **自動化:** 手動での復旧作業はミスを誘発するため、Infrastructure as Code (IaC) を用いた自動復旧が推奨される。

## 🏢 ケーススタディ

### ケース：リージョン障害発生時の事業継続

あるグローバル企業が単一リージョンのみでサービスを運用していたところ、大規模なクラウド障害により数時間にわたるサービス停止が発生しました。バックアップは取得していたものの、復旧用の環境構築が手動であったため、大幅なRTO超過を招きました。

#### 問題点

* 単一リージョンへの依存（SPOF：単一障害点）。
* 復旧手順が自動化されておらず、手動作業による人的ミスと遅延が発生。
* 障害発生時の意思決定プロセスが未整備。

#### 対応策

* 複数リージョンへのマルチリージョン構成への移行。
* Infrastructure as Code (Terraform/CloudFormation) によるDR環境の自動構築。
* 定期的なDR訓練（Chaos Engineering等）の実施。

#### ケースから学ぶ教訓

* 「クラウドだから落ちない」という過信を捨て、障害を前提とした設計（Design for Failure）を行う。
* DR計画は「作成して終わり」ではなく、定期的な検証で有効性を担保する。
