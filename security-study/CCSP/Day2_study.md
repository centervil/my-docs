## 📖 解説パート

### クラウド参照アーキテクチャの比較：CSAとNIST

クラウドコンピューティングの標準的な枠組みとして、CSA（Cloud Security Alliance）の「Enterprise Reference Architecture」と、NIST（米国国立標準技術研究所）の「SP 500-292」が広く参照されます。

NIST SP 500-292は、クラウドの役割（クラウドプロバイダー、消費者、ブローカー、監査人など）を定義し、各エンティティ間の関係性を論理的に整理したモデルです。一方、CSAのモデルはよりセキュリティに焦点を当てており、ビジネスプロセスから技術インフラに至るまでの多層的な防御戦略を統合することを目指しています。

これらを理解することで、クラウド導入時に「どのコンポーネントが誰の管理下にあるか」を構造的に把握することが可能になります。特に、クラウド利用が複雑化するマルチクラウド環境では、これらの参照モデルを指針とすることで、セキュリティの抜け漏れを防ぐための共通言語として活用できます。

### 責任共有モデルとマルチテナンシーの技術的側面

クラウドセキュリティの根幹となるのが「責任共有モデル」です。これは、クラウドプロバイダー（CSP）と顧客がセキュリティの責任を分担する考え方です。IaaSでは物理インフラとハイパーバイザまでがCSPの責任範囲となり、OS以降は顧客の責任となります。PaaSではOSやランタイムがCSP側に移り、SaaSではアプリケーション機能の多くがCSPの管理下に入ります。

また、クラウドの効率性を支える「マルチテナンシー」には、技術的な分離が必要です。
* **ハイパーバイザ**: 物理リソースを仮想マシン（VM）単位で分離し、強力な隔離を提供します。
* **コンテナ**: OSレベルの仮想化であり、ネームスペースやcgroupsを用いてプロセスを分離します。
* **リスク**: いずれの技術も「脱出（Escape）」の脆弱性が存在します。特にコンテナはハイパーバイザよりも隔離の境界が薄いため、カーネルレベルの脆弱性が攻撃対象になりやすい点に注意が必要です。

```text
# 責任共有モデルの境界線（例）
| 層 | IaaS | PaaS | SaaS |
| :--- | :--- | :--- | :--- |
| データ | 顧客 | 顧客 | 顧客 |
| アプリ | 顧客 | 顧客 | CSP/顧客 |
| OS/Runtime | 顧客 | CSP | CSP |
| インフラ | CSP | CSP | CSP |
```

#### 重要ポイント

* 責任共有モデルは「クラウドだから安全」ではなく「責任範囲に応じた対策が必要」であることを示している。
* サービスモデル（IaaS/PaaS/SaaS）が上がるほど、顧客の管理範囲は狭まるが、データ保護の責任は常に顧客に残る。
* 論理的分離は物理的分離ほど完全ではないため、共有インフラ特有の脆弱性（サイドチャネル攻撃等）への理解が不可欠。

## 🏢 ケースステディ

### ケース：SaaSにおける設定不備によるデータ漏洩

ある企業が利用しているSaaSにおいて、共有設定の誤りにより機密データが外部公開されるインシデントが発生しました。このSaaSは「アプリケーションの管理はプロバイダーが行う」という仕様でしたが、アクセス権限の設定や共有範囲の制御は利用者の責任となっていました。

#### 問題点

* 「SaaS＝すべてプロバイダーが守ってくれる」という誤った認識。
* 権限管理（IAM）の設計と定期的な見直しの欠如。
* 共有リンクの有効期限や権限スコープに対するポリシーの未策定。

#### 対応策

* 責任共有モデルを再確認し、自社の管理責任範囲を明文化する。
* SaaSのセキュリティ設定を自動監査するツールの導入。
* アクセス権限を最小権限の原則に基づき再設定し、定期レビューを義務化。

#### ケースから学ぶ教訓

* SaaSであっても、データとアクセス権の管理責任は顧客にある。
* クラウド導入前に、プロバイダーが提供するセキュリティ設定機能を網羅的に把握する必要がある。
