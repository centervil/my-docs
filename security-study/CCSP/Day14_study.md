## 📖 解説パート

### DevSecOpsの原則と「Shift Left」

DevSecOpsは、開発（Dev）、セキュリティ（Sec）、運用（Ops）を密接に連携させ、セキュリティを開発ライフサイクル全体に統合するアプローチです。従来の「開発後にセキュリティテストを行う」手法では、リリース直前の脆弱性発見により手戻りコストが膨大になるという課題がありました。

これを解決するのが「Shift Left（左へのシフト）」という考え方です。開発の初期段階（設計やコード記述のフェーズ）にセキュリティを組み込むことで、リスクを早期に特定・排除します。自動化されたセキュリティゲートをパイプラインに導入することで、人的ミスを減らし、開発スピードを落とさずに堅牢なアプリケーションを提供することが可能となります。

### CI/CDパイプラインにおけるセキュリティゲート

CI/CDパイプラインにセキュリティを統合する際は、以下のツールを自動プロセスとして組み込むのが一般的です。

1. **SAST（静的アプリケーションセキュリティテスト）**: ソースコードをスキャンし、インジェクション等の脆弱性を開発段階で特定します。
2. **SCA（ソフトウェア構成分析）**: オープンソースライブラリの脆弱性やライセンス違反をチェックします。
3. **コンテナイメージスキャン**: OSの脆弱性やパッケージの不備を検知します。
4. **IaCスキャン**: TerraformやCloudFormation等の設定ファイルをスキャンし、クラウド上の設定不備（パブリックアクセス許可など）を未然に防ぎます。

また、パスワードやAPIキーをコード内に含めるのは厳禁です。HashiCorp VaultやAWS Secrets Manager等の専用ツールを用い、動的にシークレットを注入する仕組みを構築する必要があります。

#### 重要ポイント

* セキュリティテストの自動化により、一貫した品質と迅速なリリースを両立させる。
* パイプライン上の各フェーズで適切なゲート（SAST/SCA等）を配置し、不合格時にはビルドを停止させる。
* シークレット情報はコードリポジトリに保存せず、専用の管理サービスを介して利用する。

## 🏢 ケーススタディ

### ケース：CI/CD環境におけるクレデンシャル漏洩

ある企業がGitHub Actionsを活用したCI/CDパイプラインを導入していましたが、開発者が誤ってAWSのアクセスキーをソースコード内にハードコーディングし、リポジトリにプッシュしてしまいました。その結果、攻撃者がGitHubのリポジトリからキーを盗み出し、クラウドインフラへの不正アクセスを許すというインシデントが発生しました。

#### 問題点

* クレデンシャル（認証情報）がソースコードとともに管理されていた。
* リポジトリへのプッシュ前にシークレットを検出する仕組みがなかった。
* 最小権限の原則に基づいたIAMロールの設計が不十分であった。

#### 対応策

* シークレット管理ツール（AWS Secrets Manager等）の導入とコードからの分離。
* git-secrets等のツールを用いた、コミット前のシークレット検出の自動化。
* GitHub ActionsのOIDCプロバイダーを利用し、長期間有効なキーの使用を廃止する。

#### ケースから学ぶ教訓

* ソースコードは常に外部公開される可能性があるという前提で設計する。
* 認証情報は環境変数や専用の管理サービスに分離し、コードとは完全に切り離す。
* 自動化ツールを導入し、人間によるミスを技術的に防ぐ仕組みを構築する。

## 📋 今日のまとめ

* DevSecOpsの「Shift Left」により、早期の脆弱性特定とコスト削減を実現する。
* CI/CDパイプラインにSAST/SCA/IaCスキャンを組み込み、セキュリティゲートを自動化する。
* シークレット情報は管理ツールを用いてセキュアに管理し、コードへの混入を徹底して防ぐ。
