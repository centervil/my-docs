## 📖 解説パート

### APIセキュリティの基本と防御手法

クラウドネイティブなアーキテクチャにおいて、APIはシステム間連携の要です。しかし、公開されたAPIは攻撃の標的となりやすいため、適切な防御層を構築する必要があります。

まず、**認証と認可**はAPIセキュリティの基盤です。APIキーは簡易的ですが、機密性の高い通信にはOAuth 2.0やOpenID Connectを用いたトークンベースの認証が推奨されます。これにより、ユーザーの権限に基づいた適切なアクセス制御が可能になります。

次に、**レート制限（Rate Limiting）**は、DoS攻撃やブルートフォース攻撃からリソースを保護するために不可欠です。API Gatewayを用いて、特定のIPアドレスやユーザー単位でのリクエスト回数を制限することで、異常なトラフィック流入を抑制します。また、**入力バリデーション**を徹底し、SQLインジェクションやコマンドインジェクションのリスクを排除することも重要です。

### OWASP Top 10とWAFによる保護

WebアプリケーションおよびAPIに対する攻撃手法は日々高度化しています。**OWASP Top 10（2021）**および**OWASP API Security Top 10**は、現在の脅威状況を理解するための標準的なガイドラインです。特にAPIにおいては、BOLA（Broken Object Level Authorization：オブジェクトレベルの認可不備）や、過度なデータ露出などが主要なリスクとして挙げられます。

これらへの対策として、**WAF（Web Application Firewall）**の導入が有効です。WAFはHTTP/HTTPSトラフィックを検査し、既知の攻撃パターン（SQLiやXSSなど）をブロックします。運用においては、以下の点が重要です。

* **ルールセット管理**: 最新の脅威情報に基づいてルールを更新し続けること。
* **偽陽性（False Positive）対応**: 正当なアクセスをブロックしないよう、監視モードで検証してから適用する。
* **ログ分析**: 攻撃の傾向を把握し、セキュリティポリシーの最適化に活かすこと。

#### 重要ポイント

* 認証にはAPIキーだけでなく、OAuth 2.0等の堅牢なプロトコルを使用する。
* API Gatewayをフロントに配置し、レート制限と入力バリデーションを適用する。
* WAFを導入し、OWASP Top 10等の既知の脆弱性パターンを継続的に監視・防御する。

## 🏢 ケースステディ

### ケース：APIを介した個人情報漏洩

ある企業が顧客向けに公開したREST APIにおいて、特定のIDを指定することで認証なしに他者の個人情報が取得できてしまう脆弱性（BOLA）が発覚しました。攻撃者はこの脆弱性を悪用し、短時間で数万件の個人情報をスクレイピングしました。

#### 問題点

* オブジェクトレベルの認可チェックが実装されていなかった。
* APIの利用頻度に対する監視やレート制限が設定されていなかった。
* 脆弱性診断（SAST/DAST）が開発ライフサイクルに組み込まれていなかった。

#### 対応策

* 全てのAPIエンドポイントに対して、認可ロジックを強制するミドルウェアの実装。
* API GatewayにてIP単位・ユーザー単位のレート制限を適用。
* 定期的なAPI脆弱性診断の実施と、OWASP API Security Top 10に基づくコードレビューの導入。

#### ケースから学ぶ教訓

* 「認証（誰か）」と「認可（何ができるか）」を混同せず、常にリソース単位で厳格なアクセス制御を行う。
* APIの公開は、防御機能（API Gateway等）とセットで設計する。
* 開発段階でセキュリティを考慮する「セキュリティ・バイ・デザイン」を徹底する。
